# Проверка архива погоды, координат и времени

Проверено 23 сентября 2026 года реальными HTTP-запросами. Область работы: доступность источников и временная корректность; прогнозная модель не строилась.

**Последующее уточнение:** пользователь подтвердил время CSV **UTC+5**. В текущем расчёте применяется фиксированное смещение +05:00. Ниже сохранены результаты первоначальной проверки до этого уточнения; вопросы о неизвестном поясе относятся к прежнему состоянию. Актуальные прогнозы и метрики: [отчёт модели](../../outputs/baseline/REPORT.md). Начало/конец десятиминутного интервала остаётся отдельным допущением.

## Результат

- Координаты обеих турбин подтверждены перенаправлениями Google Maps из исходного PDF.
- Архив отдельных запусков NOAA GFS доступен для всего тестового периода. Проверены 29 ежедневных запусков 12:00 UTC с 31 января по 28 февраля 2026 года.
- Для каждого запуска найдены все 48 прогнозных часов `f007`–`f054` и соответствующие `.idx`: всего 1 392 прогнозных часовых записи и 2 784 объекта. Это перекрывающиеся прогнозы, а не 1 392 уникальных часа февраля.
- Все выбранные файлы и индексы имеют S3 `LastModified` не позднее 18:00 UTC дня запуска. Это проверенный пример времени отсечения, а не установленное организаторами расписание.
- Open-Meteo Previous Runs вернул 1 464 последовательных часа за 01.01–02.03.2026, по девять переменных для каждой точки, без пропусков и нечисловых значений.
- Гражданский часовой пояс координат — `Asia/Almaty`. Часовой пояс самих CSV по имеющимся сведениям не установлен.

## Основной источник: отдельные запуски NOAA GFS

Официальный каталог: https://registry.opendata.aws/noaa-gfs-bdp-pds/

Индексы объектов получены через публичный S3 ListObjectsV2:

```text
https://noaa-gfs-bdp-pds.s3.amazonaws.com/?list-type=2&prefix=gfs.20260131%2F12%2Fatmos%2Fgfs.t12z.pgrb2.0p25.f0&max-keys=200
```

В этих списках проверено наличие каждого нужного ключа и время `LastModified`; усечённость списка после 200 ключей не влияет на проверенные `f007`–`f054`.

В индексе `gfs.20260131/12/atmos/gfs.t12z.pgrb2.0p25.f024.idx` подтверждены:

- `UGRD:100 m above ground` — зональная компонента ветра;
- `VGRD:100 m above ground` — меридиональная компонента ветра;
- `TMP:2 m above ground` — температура на 2 м.

Проверен доступ к самому бинарному файлу: Range-запрос байтов `497823535–497823550` вернул HTTP 206 и 16-байтовый заголовок GRIB edition 2 поля UGRD. Это позволяет получать отдельные поля по диапазонам байтов вместо загрузки всего файла размером около 539 МБ. Поля ещё не декодировались в значения в точке; наличие переменных проверено на одном индексе, а не на всех 1 392 файлах. Высоту ступицы турбины нужно уточнить отдельно.

Для начала январской валидации дополнительно проверено наличие `f007`–`f054` в запуске 01.01.2026 12 UTC. Все январские запуски NOAA и весь архив с марта 2023 в этом шаге не проверялись.

### Пример воспроизведения без поздних выпусков

Если выбрать расчёт ежедневно в 18:00 UTC и использовать запуск того же дня 12:00 UTC:

| Событие | UTC | Местное гражданское время в феврале 2026 |
|---|---|---|
| Инициализация модели | 31.01 12:00 | 31.01 17:00 |
| Время отсечения данных | 31.01 18:00 | 31.01 23:00 |
| Первый целевой час, `f007` | 31.01 19:00 | 01.02 00:00 |
| Последний целевой час, `f054` | 02.02 18:00 | 02.02 23:00 |

Для этого запуска последний из 96 используемых объектов опубликован в 15:59:20 UTC, то есть раньше отсечения. Аналогичная проверка выполнена для всех 29 дат.

В реализации сохранять `forecast_origin`, `run_time`, `valid_time`, `lead_hours`, S3 key, `LastModified` и ETag. Проверять `max(LastModified файла, LastModified индекса) <= forecast_origin` и не заменять выбранный выпуск более поздним. Расписание выпуска и значения временных меток CSV требуют отдельного согласования.

## Быстрый API: Open-Meteo Previous Runs

Документация: https://open-meteo.com/en/docs/previous-runs-api

Проверены модель `gfs_global`, единицы ветра `ms`, время `UTC`, даты 01.01–02.03.2026 и обе пары координат. Для смещений `previous_day1`, `previous_day2`, `previous_day3` получены:

- `wind_speed_100m`;
- `wind_direction_100m`;
- `temperature_2m`.

На каждый ряд приходится 1 464 значения; пропусков нет. Полный ответ сохранён в `raw/openmeteo-gfs-20260101-20260302.json`. Отдельный запрос `timezone=auto` подтвердил `Asia/Almaty` и UTC+05 для февраля 2026.

Previous Runs объединяет значения разных запусков с фиксированным смещением упреждения. Ответ не содержит точного `run_time` и исторического времени публикации для каждой точки. Поэтому наличие этих данных не доказывает возможность восстановления произвольного единого выпуска, доступного к заданному отсечению.

Проверка исходного кода Open-Meteo показывает: слой `previous_dayN` обновляется начиная с `run + N * 24h`. При непрерывной последовательной обработке шестичасовых циклов GFS это соответствует примерно `run = floor_6h(valid_time - N * 24h)`; фактическое упреждение составляет 24N–24N+5 часов. Это свойство алгоритма, не подтверждение происхождения каждого исторического ответа.

Источник кода: https://github.com/open-meteo/open-meteo/blob/fb7e8046633bafe1244e16abf1c1491bae48ecca/Sources/App/Helper/OmFileSplitter.swift#L349

Для строгого воспроизведения рекомендуются подтверждённые отдельные выпуски NOAA. Previous Runs можно использовать для предварительных экспериментов при явно описанной политике выбора данных; подменять архив прогнозов фактической погодой нельзя.

## Время CSV: что известно и что не установлено

Гражданское время местности:

- до 29.02.2024 18:00 UTC — UTC+06;
- начиная с этого момента — UTC+05;
- при переходе местный час 29.02.2024 23:00–23:59 повторился.

Подтверждение: постановление Правительства Казахстана №20 https://primeminister.kz/ru/decisions/19012024-20 и правила IANA https://data.iana.org/time-zones/tzdb/asia.

В обоих CSV отсутствуют UTC-смещение и метаданные часового пояса. На 29.02.2024 приходится ровно 144 строки, каждая метка 23:00–23:50 встречается один раз; далее идёт 01.03 00:00. Дубликатов временных меток во всём файле нет.

Это не позволяет различить UTC, фиксированное смещение +05/+06, местное время с обработкой повторов или иной способ экспорта. Географический часовой пояс нельзя автоматически присвоить временам SCADA. При гипотезе `Asia/Almaty` шесть строк 29.02.2024 23:xx в каждом CSV неоднозначны.

До уточнения хранить исходные метки неизменными, погоду получать в UTC, а преобразование времени CSV оформить явным параметром. Не выбирать повторный час автоматически и не считать временную гипотезу доказанной по одной корреляции.

Вопрос организаторам:

> В каком часовом поясе записан столбец «Статистическое время»: UTC, фиксированный UTC+5/UTC+6 или местное Asia/Almaty с переводом часов 1 марта 2024 года? Менялось ли время SCADA или выполнялось преобразование при экспорте? Как обработан повторный час 29 февраля 23:00–23:50? Метка означает начало или конец десятиминутного интервала? В какое время необходимо выпускать ежедневный прогноз?

## Файлы проверки

- `verification.json` — краткая машинно-читаемая сводка и SHA-256 исходных ответов;
- `noaa-coverage.json` — все проверенные S3-объекты с временем публикации и ETag;
- `raw/` — ответы Open-Meteo, списки NOAA, пример индекса и заголовок GRIB;
- `verify.py` — повторная проверка сохранённых ответов без сетевых запросов, обучения и изменения исходных CSV.

Повторить проверку:

```sh
python3 research/weather-check/verify.py
```

Проверка использует только стандартную библиотеку Python и актуальную базу IANA часовых поясов.
